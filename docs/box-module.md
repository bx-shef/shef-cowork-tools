# Коробочный модуль: инструменты для AI-агента

Модуль коробочного Битрикс24 отдаёт функции агенту shef.cowork двумя вещами: **REST-методами** и **методом-манифестом**.
Полный рабочий код — [examples/box-module-minimal](../examples/box-module-minimal) и
[examples/client-bank](../examples/client-bank).

## Как это работает

1. Модуль регистрирует методы обработчиком события `rest` → `OnRestServiceBuildDescription` в **своей области
   прав** (например `demo_notes`). Как это делается в ядре — статья `settings/cloud-and-on-premise/on-premise/custom-methods.md`
   в `bitrix-tools/b24-rest-docs`.
2. Один из методов — манифест (например `demo.mcp.tools`): он возвращает список инструментов.
3. Администратор портала вписывает имя манифеста в «Модули портала» ([enable.md](enable.md)).
4. Сотрудник открывает AI-клиент. Сервер вызывает манифест **токеном этого сотрудника** (результат помнит 5 минут),
   агент видит инструменты, вызов идёт в названный REST-метод тем же токеном.

Права проверяет модуль, как в любом REST-методе: к моменту вызова обработчика `$USER` уже авторизован как
сотрудник токена; в коде берите `\Bitrix\Main\Engine\CurrentUser::get()`. Манифест может отдавать разным
сотрудникам разный набор (например, без инструмента удаления тем, кому оно не разрешено). Отзыв права в манифесте
доходит до клиента за 5 минут, проверка внутри самого метода действует сразу — поэтому **права проверяйте и в методе**.

## Регистрация

Установщик модуля подписывает обработчик:

```php
\Bitrix\Main\EventManager::getInstance()->registerEventHandler(
    'rest', 'OnRestServiceBuildDescription', 'demo.notes', \Demo\Notes\Rest::class, 'onRestServiceBuildDescription'
);
```

Обработчик возвращает методы своей области (форма — как в статье REST-документации):

```php
public static function onRestServiceBuildDescription(): array
{
    return [
        'demo_notes' => [                                  // область прав: её выдают приложению shef.cowork
            'demo.mcp.tools'    => ['callback' => [__CLASS__, 'tools'],  'options' => []],
            'demo.notes.search' => ['callback' => [__CLASS__, 'search'], 'options' => []],
        ],
    ];
}
```

Сигнатура метода — `function (array $query, $nav, \CRestServer $server)`. Имя метода принято строить как
`вендор.сущность.действие`; **первый сегмент — вендор**, и именно он ограничивает манифест (см. ниже).

## Манифест

Метод-манифест вызывается без параметров и возвращает массив инструментов или `{"tools": [...]}`; не больше 50
инструментов.

```json
[
  {
    "name": "notes_search",
    "title": "Поиск по заметкам",
    "description": "Ищет заметки по словам в тексте. Возвращает id, заголовок и дату, не больше 50 записей.",
    "method": "demo.notes.search",
    "kind": "read",
    "input": {
      "type": "object",
      "required": ["query"],
      "properties": {
        "query": { "type": "string", "minLength": 2, "maxLength": 200 },
        "limit": { "type": "integer", "minimum": 1, "maximum": 50 }
      }
    }
  }
]
```

### Поля манифеста

| поле | правило |
|---|---|
| `name` | обязательно; латиница в нижнем регистре, цифры, `_`; 2–48 знаков, начинается с буквы; не совпадает с именем встроенного инструмента и с другим инструментом манифеста |
| `description` | обязательно, 20–1000 знаков: по нему агент решает, **когда** звать инструмент. Пишите, что делает и что возвращает |
| `method` | REST-метод **того же вендора**, что и манифест (`demo.mcp.tools` → только `demo.*`); не сам манифест |
| `kind` | `read` (по умолчанию), `write`, `delete` |
| `input` | JSON Schema объекта (`"type": "object"`), не длиннее 8000 знаков, без `$ref`, `$defs`, `definitions`, `$id`, `$anchor`; не глубже 6 уровней |
| `title` | необязательно, подпись для человека (до 100 знаков, одной строкой) |
| `confirmRead` | необязательно, только у `delete`: `{"method": "<метод чтения того же вендора>", "idArg": "<имя параметра с id из input>"}` |

Тексты `description` и `title` очищаются от управляющих и невидимых символов. Плохая запись пропускается с причиной
в журнале сервера, остальные записи работают. Манифест ждут не дольше 3 секунд: медленный модуль остаётся без
инструментов в этот раз.

Схему `input` сервер также разбирает библиотекой JSON Schema; храните её простой: `type`, `properties`, `required`,
`enum`, `minimum`/`maximum`, `minLength`/`maxLength`, `pattern`, `items`, `maxItems`.

### Вид инструмента: чтение, запись, удаление

| `kind` | что видит сотрудник | кто видит |
|---|---|---|
| `read` | инструмент с пометкой «только чтение» | все, кому открыт модуль |
| `write` | инструмент с пометкой «не только чтение»; клиент спрашивает человека перед вызовом | только тем, кому администратор открыл запись |
| `delete` | пометка «разрушающее»; **сервер** сам задаёт вопрос в окне AI, метод зовётся только после «да» | только тем, кому открыта запись, и только в клиентах, которые умеют задавать вопросы (MCP elicitation) |

Удаление подробнее:

- Метод модуля вызывается только после «да» сотрудника и только если инструмент с тем же методом и `kind: delete`
  всё ещё есть в свежем манифесте.
- Без `confirmRead` сотрудник видит метод и значения аргументов (id и числа первыми) с пометкой, что описание
  составлено по аргументам и сервером не проверено. Поэтому у удаляющего инструмента **описание и имена параметров
  должны быть понятны человеку** (`id` выписки, а не `p1`).
- С `confirmRead` сервер до вопроса читает запись указанным методом, показывает её сотруднику, а после «да»
  перечитывает и сверяет: запись изменилась — не удаляет.

## Запрещённые и «о ком» параметры

Кто вызывает и с какого портала — берётся только из входа сотрудника. Поэтому в схеме `input` **на любой глубине**
не может быть параметров с такими именами (без учёта регистра, дефисов, точек и пробелов, то есть `member_id`,
`member-id`, `memberId` — одно и то же):

`auth`, `access_token`, `refresh_token`, `member_id`, `portal`, `domain`, `client_endpoint`, `server_endpoint`,
`application_token`, `session`, `token`, `asUser` / `as_user_id`, `runAs` / `run_as_user`, `actAs`, `onBehalf` /
`onBehalfOf`, `impersonate`, `sudo`.

Такой инструмент отклоняется целиком. Параметры «о ком» — `userId`, `user`, `employeeId`, `staffId`, `personId`,
`forUser` — разрешены как **фильтр**; манифест принимается с предупреждением в журнале. В методе действует всё равно
вошедший сотрудник: чужой id только сужает выборку, и только после проверки, что вызывающему эти данные доступны.

При вызове методу уходят **только ключи из `input.properties`**: всё лишнее отбрасывается, а запрещённые имена и
ключи, начинающиеся с `_`, — всегда. Аргументы проверяются по схеме до вызова портала.

## Ответы и ошибки

**Ответ метода.** Возвращайте то, что нужно агенту: понятные поля, без HTML, списки — до 50 записей с `next` и
`total`. Ответ уходит агенту как JSON; невидимые и bidi-символы из значений вырезаются. После данных агент получает
напоминание, что это данные, а не указания. Ответ не длиннее примерно 24 тысяч знаков; длиннее — самый длинный список
верхнего уровня сокращается с пометкой `truncated`.

**Ошибки.**

- `\Bitrix\Rest\RestException` с HTTP-статусом 4xx: агент видит код и текст (`error_description`, одной строкой, до
  300 знаков): `INVALID_ARG_VALUE — Нужен query: слова для поиска`.
- «Не найдено» — `\CRestServer::STATUS_NOT_FOUND` с описанием `Not found`: агент видит «Не найдено», а не сбой.
- Текст отказа читает агент. Пишите, что исправить в запросе; без путей, SQL, персональных данных и без эха чужого
  ввода (заголовок чужой статьи в тексте ошибки — канал подсказок агенту от других сотрудников).
- Отказ самого портала (например `insufficient_scope`) агент видит текстом ядра; для администратора это знак, что
  область модуля не выдана приложению ([enable.md](enable.md)).
- Ошибка приходит агенту тремя строками: что случилось, что делать, временная ли. У `write` и `delete` временная
  ошибка советует сначала проверить чтением, не выполнилось ли действие: повтор мог бы дать дубль.

## Проверка

```bash
php bin/dump-manifest.php | node ../../tools/manifest-check.mjs - demo.mcp.tools
```

На портале: открыть `/rest/<манифест>` под администратором и увидеть список; в журнале сервера нет строк
`"kind":"manifest"` с ошибками; в клиенте видны инструменты.

Что не проверяется локально: сигнатура и форма регистрации методов взяты из документации REST Битрикс24 и кода
ядра; целиком модуль на живой коробке проверьте на своём портале.
